# 历史源家族安全转冷与同 owner 重新载入（C10）

本批在 [C9 长前缀重放](kv-lifecycle-source-replay.md) 上补齐显式转冷：保留已提交的磁盘源记录，
释放其 RAM 源记录及原生历史别名，然后允许同一个 Engine 再次导入。阶段 C 和完整六阶段目标
继续开放。本页的执行结论以本批 [执行摘要](experiments/2026-10-31-lifecycle-source-cool/summary.json)
为准；新增 API 不等于完整生产验收。

## 修改前后

此前可以保存源记录、重启后导入、从源记录重算，或者永久遗忘整个家族；同一归档 key 在一个
owner 中已有 RAM binding 时不能再次导入。因而只有永久删除或关闭 owner 才能解除该绑定，
缺少“腾出 RAM、继续保留恢复依据”的入口。

现在增加两个公开 Engine 方法：`cool_historical_source(ref)` 与 `cool_historical_archive(key)`。
结果分别报告此次实际转冷的 RAM 源数、撤销的原生域数，以及这些 RAM 源对应的保留归档数。
最后一项不是整个 namespace 的记录总数。已经全冷的归档家族再次调用返回零，归档 key 仍有效。
`forget_historical_source/archive` 继续表示永久遗忘，两者不能互相代替。

## 一次转冷的提交顺序

1. Engine 必须空闲：没有执行中、尚未消费完成的请求或原生状态事务。Program 继续检查
   continuation/传输 owner；不能绕过 ResourceManager 撤销还在使用的设备句柄。
2. 收集持久归档家族的所有 RAM bindings 及 RAM 后代，包括分别导入、在 RAM 中成为新根的
   持久子孙。与永久遗忘共用已有有界家族预检，不新建目录或后台线程。
3. 检查每个待释放源都已有**完整当前版本**的已发布快照。仅保存父源、子孙尚未保存，或
   保存后又 append/推进 computed revision，都不足以允许转冷。任何失败均保留整个在线家族。
4. 逐文件重新验证当前 blob 的实际长度和校验和；使用固定 8 KiB 栈缓冲流式读取，不建立完整
   R 副本。截断、损坏、缺文件或 I/O 失败都在修改之前返回。
5. 预检所有原生别名并准备好必要替换对象后，在同一个串行控制操作内解除 binding、关闭旧
   RAM 引用并先删子孙再删父源，随后清理原生历史/coverage/checkpoint 别名。此提交阶段不再
   分配或写磁盘；新执行看不到“源已删除而别名还可使用”的中间状态。

公共组件的 `SourceArchive::cool_sources` 只承担归档验证、RAM 后代闭合、解绑和 RAM 删除。
adapter 必须负责其原生 owner 预检及同一控制操作内的别名清理。当前由 NInfer Program 完成，
没有把原生 KV 所有权移进公共归档组件。

## 为什么重新导入不会复活旧状态

归档 Entry 增加一个仅在运行时使用的 `bound_snapshot_revision`。保存发布时它记录所保存 RAM
版本；导入时记录本次新 RAM binding 的版本。它不写入磁盘 catalog/blob，旧磁盘镜像中的源 ID、
revision、parent 和 computed 都只是来源信息，不能授权复用本次 owner 的旧计算状态。

成功转冷保留 durable key 和当前 read receipt 的读取资格，但删除旧 RAM 源身份。重新导入
建立单调增加的新源 ID、新 RAM 根和 computed=0；模型需要在新域重算。旧准备对象会得到 Stale，
旧 binding 创建的保存工单即使 I/O 已完成，也不能在转冷后或重新绑定后发布。下一次对重新
导入且未变化的源转冷，不要求把同一份数据无意义地再写一遍。

两个现有 Entry 表都按 M 计费，新增 revision 字段随这两张表一起计入预算；不是未计费的
旁路 map。当前 256 槽配置新增约 4 KiB 字段存储，实际准入仍使用 `sizeof(Entry)` 计费。
RAM 删除顺序使用同一活 journal 内单调分配的源 ID，不能据此跨进程比较 revision 或 ID 新旧。

## 实际验证内容

组件测试覆盖当前/未发布/过期版本、未保存子孙、缺文件、截断和损坏、重复或外来引用、读回执、
迟到 writer、持有中的恢复副本，以及小 ID 夹具下禁止新分配的成功提交。检查磁盘 catalog/seal
在转冷中不变；永久遗忘仍撤销读取资格和持久家族。

真实模型测试使用与 C9 相同的 Qwen3.8-27B artifact、Linux 单 GPU/单并发、rk4v4、meanq-cosine、
max 聚合、graph=0、context cache 关闭、device profile=off、selected=2048、reserve/prefill=512、设备窗口=2560、H=96 MiB、C=2048 MiB、
S=16 MiB、R=1 MiB、M=64 MiB，归档 D=64 MiB、metadata=1 MiB，分别检查 LRU/redundancy 与
普通解码/MTP4。新循环的根/子/无关源输入长度为 1024/768/512，各生成 8 token，准备 completion=32。
这是独立原生测试程序的固定输入，不是 HTTP/CLI 配置验收。

每组同时检查忙碌拒绝、未保存子孙和损坏文件的原子拒绝、实际 S/H 字节下降、持有的 7168 bytes
R 直到旧准备对象退出才退款、旧 writer 拒绝、同 owner 多次重新导入、混合 RAM 根/后代转冷、
独立原始输入输出一致、永久遗忘后的重启拒绝及无关家族继续可用。MTP4 还要求实际 speculative
rounds 非零。另从真实 C9 已验收目录复制旧归档和当时的独立原始输入输出 oracle，转冷、再次
导入、完整重放 32K，再换新进程重开重放，验证磁盘格式及恢复依据确实保留。

## 本批最终结果

Windows 23 项公共契约、Linux 24 项 Debug 及同 24 项 ASan/UBSan/泄漏检查、原生 12 项接口与预算
检查和 2 项组件检查均通过。转冷新增 10 个独立模型进程、当前 C9 重放/兼容 14 个、C8 归档
17 个及既有 GPU 七组均通过；七组中的 pinned-pool 检查不是语言模型推理，不能把 48 项统称
为 48 次模型质量评测。真实旧 C9 归档的两次完整 32K 重放各执行 64 个不超过 512 token 的
原生单元，实际覆盖区间无缺口，输出与原 C9 原始输入 oracle 一致。

四种新循环的第一次转冷均实际删除 2 个 RAM 源并撤销 2 个原生域、保留 2 个对应归档；后续
混合导入新根/重算分支实际转冷 3 个源。各组观测字节如下（这是固定夹具内存效果，不是 RSS）：

- `lru-none`：S 62,208 → 47,360 bytes；H 44,728,320 → 10,321,920 bytes。
- `lru-mtp4`：S 62,208 → 47,360 bytes；H 47,523,840 → 10,967,040 bytes。
- `redundancy-none`：S 62,208 → 47,360 bytes；H 44,728,320 → 10,321,920 bytes。
- `redundancy-mtp4`：S 62,208 → 47,360 bytes；H 47,523,840 → 10,967,040 bytes。

十个已有程序中八个二进制发生变化，因此重新运行受影响的全部回归；两个独立 checkpoint
契约程序身份未变，也在本批重新执行。148 项契约输入、3455 项实际原生输入固定；第 33 补丁
从 C9 源码树独立重放一致。公共 host 内存检查不等于完整 CUDA 内存检查，历史 TSan 工具进入
应用前失败仍无通过结论。原生导出源码的 unknown build-id 提示及 filesystem/NVML 弃用编译警告保留。

首个控制任务在后续 redundancy 长重放回归中退出 1：取消检查失败，日志显示两次重放都完成了
整个 32K。检查发现取消回调先同步调用遗忘接口，可能等待执行锁并阻塞同一消费者线程转交取消。
现在用独立的 128-token 请求及未消费 handle 检查忙碌拒绝，然后消费并遗忘该无关探针；取消
回调只设置标志。32K 主负载、至少 4096 token 后且未完成时取消、半成品不得发布等断言保留，
修正后的全部 14 项重放回归重新执行。该修正只改测试，没有修改产品运行时代码。

十项新增转冷测试在首个控制任务后来失败之前已经完成；修正前后产品源码及其可执行文件逐
字节相同，故保留这十项有效结果，不把后续失败隐藏或把未完成任务写成通过。原失败执行、
partial 报告和日志随证据包保留，摘要明确记录复用范围。测试准备脚本还曾在任务启动前出现
语法笔误，修正时未运行产品代码。原始输入、日志、JUnit、控制脚本与报告保存在本地
`artifacts/lifecycle-source-cool/evidence.zip`，摘要记录大小与 SHA-256。

## 成本、边界与后续

这是空闲 Engine 下的显式入口，尚未接上自动源容量策略、后台调度或 HTTP/CLI。同步读取并验证
所有目标 blob 会阻塞控制调用；不在 decode 临界区执行，也没有声称延迟或吞吐不变。
忙碌调用也可能先等待执行锁再返回 Pending，不能在负责转交取消信号的进度回调内同步等待它。

释放 S/H 不等于全部内存立即归零：调用方持有的旧准备对象继续占真实 R，保存工单继续占真实
D，直到相应 owner 退出。C 中付费的可复用空闲池也可能保留物理 buffer。当前设备工作集仍由
原生执行器管理；不能把这个家族转冷接口当成 GPU 活动页回收策略。

文件长度/校验和沿用可信本地文件系统模型，不是恶意并发改写防护或硬件断电证明。现有
catalog/seal 部分提交会拒绝整个归档重开，整体备份回滚没有外部单调锚点，这些限制未消失。
归档和 RAM 目录仍有 256 槽的有限几何，S 满时没有隐式永久遗忘或自动转冷。

下一步仍须补齐 checkpoint 持久恢复、精确兼容旧轨迹及版本闭环，再落实任务价值、分层/多会话、
长时间资源/质量/性能验收。当前源重算不承诺旧稀疏/recurrent 轨迹或 dense 等价；复杂真实输入、
其他配置、原生 Windows、多 Engine、完整 RSS 上界和 Agent 质量不由本批证明。DeepSWE 和主机
调试设置继续遵守用户原约束。
