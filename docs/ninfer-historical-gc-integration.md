# Historical KV GC on NInfer: integration and acceptance record

This branch gives the pinned NInfer backend opt-in `--kvmem-gc-lru` and `--kvmem-gc-redundancy` modes. Both use the same Host-page lifecycle: the policy proposes victims; the native adapter checks protection, tombstones committed pages, detaches Host records at a safe foreground boundary, and the worker releases them after readers finish. The redundancy mode uses the portable strategy rather than renaming LRU. The modes are mutually exclusive. NInfer results are separate from llama.cpp results.

## Native design

- NInfer uses 64-token Host pages. Only complete, sealed pages enter GC. Sink, recent, active-window, image, query-selected, checkpoint-resident and in-flight append pages remain protected. A protected page may be a redundancy witness but cannot be retired. Retired pages are excluded from Query, Pressure and checkpoint selection.
- The foreground copies each sealed page's Mean-K descriptor once into `HistoricalKvPageFeatures`. The GC worker reads an immutable descriptor and a frozen importance snapshot; it never reads mutable NInfer or CUDA state directly. The same page manager accepts an injected LRU or redundancy policy.
- Redundancy mode requires `--kvmem-query-scorer meanq-cosine`. NInfer's normal prefill accumulates accepted Mean-Q for the whole input Query. The foreground publishes updated page scores at most every 1,024 accepted tokens and at Query completion. This also covers long requests for which native working-set retrieval skips Query replay. The GC worker refreshes importance before ranking without repeating Query dot products. Sampled generated-output attention can raise a page's importance; successfully accepted thinking tokens mark the thinking-priority tier.
- Redundancy comparisons use at most 56 pages per round, with age-stratified older candidates and a recent segment. The policy distinguishes proven direct substitutes above cosine 0.9 from capacity fallback victims. An audit log records reason, importance, similarity and retained witness for each proposal. This is a bounded approximation, not an all-history pairwise proof.
- Native Host admission uses physical capacity. Low/high free-page watermarks include headroom for the next prefill burst. The adapter currently allows one active request because independent sequence directories do not coordinate one shared Host budget. Rollback truncates discarded descriptors and thinking ranges; when no proven thinking span remains it disarms thinking-only selection.
- The backend is pinned to `63428ac249da` plus 19 ordered patches. `backends/versions.json` records the SHA-256 of the redundancy and thinking-fallback patches and the exact prepared source tree.

- A 7,635-token request returned HTTP 200, final answer `599`, and 79 proposed/committed/reclaimed Host pages. Across the two long requests, audit logs recorded 109 `redundancy` proposals and 49 `capacity_fallback` proposals; the latter are lossy capacity deletions and must not be presented as proven duplicates.
- An earlier redundancy build returned HTTP 500 on the third request because rollback removed all thinking spans but left thinking-only selection armed. Truncation now disarms when no proven span remains; the repeated third request returned HTTP 200.
- An isolated Terminal-Bench 2.1 `cancel-async-tasks` pilot exercised the **LRU** service API and tool calls. The first run's verifier could not install `uv` and has no quality conclusion. The task did not put the 256 MiB Host pool under GC pressure. This is not a redundancy benchmark or proof of a GC-caused quality loss.

## Long-decode capacity regression and preliminary latency comparison, 2026-10-30

- A repeatable isolated runner is in `scripts/ninfer_gc_acceptance.py`. It starts a fresh model container for every mode/request, keeps raw streamed responses and native server logs, and treats an SSE `stream_error` as failure even when the HTTP status is 200. Each container resets model and Host KV state. The 9-case short matrix (off/LRU/redundancy x arithmetic/needle/sequence) passed all exact answer checks; both GC modes reclaimed about 79-80 Host pages per case. The first matrix launch had a runner readiness race and is excluded; `acceptance-20261030-rerun1` is the valid matrix.
- A 5,120-token, 16K-context stress request exposed a real redundancy-mode capacity failure. With a 160 MiB Host pool and 5,120-token generation reserve, the old code emitted an SSE `stream_error: native KV RAM capacity exhausted` after roughly 2,900 output tokens, although HTTP remained 200. The same profile in LRU mode completed 5,120 tokens. Once the preferred thinking tier had no selectable sealed page, redundancy stopped proposing victims while unclassified Host pages still occupied capacity.
- NInfer now opts in to the portable policy's cold unclassified-page LRU fallback only when its preferred thinking/reply tier has no selectable victim. Sink, mandatory and active pages remain protected; proposals carry the page's content version and are revalidated at commit. The default portable policy remains unchanged for llama.cpp. The audit marks these as `lru_fallback`, distinct from proven `redundancy` and lossy `capacity_fallback`. A Host regression covers a protected-only thinking tier and a stale prior incarnation. The final native binary rebuilt successfully after the last stale-page filter; its final IQ3 arithmetic request returned HTTP 200, answer `599`, 80 committed/reclaimed pages: 54 redundancy, 25 capacity fallback, 1 LRU fallback.
- The 5,120-token profile has three results per mode; the repaired redundancy mode was repeated three times, with mode order varied. Every request completed 5,120 output tokens with `finish_reason=length`, passed the checked output prefix, and had no SSE error. Redundancy reclaimed 123, 122 and 123 Host pages. Its first run used LRU fallback for all 123 proposals; the next two used 28 redundancy and 94-95 LRU fallback proposals. The stress checker verifies the first 100 numbers in order and at least 1,000 numbers emitted; it does not claim the requested 1-2,000 list was completed. The final stale-incarnation filter was added after these long runs, then covered by the Host test and the final native rebuild plus short IQ3 request.
- The observed p95 of intervals between streamed decode-round timing samples (ms, three runs each) was off: 63.757/66.652/66.756, LRU: 63.980/67.103/64.972, redundancy: 63.355/63.830/66.022. The respective means were 65.722, 65.352 and 64.402 ms. Mean reported decode throughput was 68.155, 68.654 and 69.593 tokens/s. These are preliminary observations, not a demonstrated speedup or a formal <=5% tail-latency result: MTP4 batches multiple tokens in 1,234 of 1,252 observed intervals, so these p95s are per decode round, not per token. GC-off needed a 256 MiB Host pool to finish while GC modes used 160 MiB. Differences in memory allocation and run order also limit causal comparison.
- Evidence is under `/tmp/kvmem-ninfer-gc-20261028/acceptance-decode-5120-repeat2`, `acceptance-decode-5120-repeat3`, `acceptance-decode-gc-5120-fallback-20261030`, `acceptance-decode-gc-5120-lru-20261030`, and `acceptance-final-source-20261030`. The first GC-off record is separately under `/tmp/kvmem-ninfer-gc-20261030/acceptance-decode-5120-off-final`. The original failing redundancy record is retained in `acceptance-decode-gc-5120-20261030`. These are isolated acceptance requests, not Terminal-Bench rewards.
## Acceptance boundary

Native LRU and redundancy mode, Host-page retirement under pressure, MTP continuation, full accepted input Query scoring, and a different-prefix reset have been exercised. This is an integration acceptance, not a claim of superior task reward or throughput. The 96 MiB pool deliberately forces GC on an 8K prompt; it is not the teacher's 256K historical budget. Native 64-token pages and at least one recent page differ from the earlier llama.cpp 32/0 setting. There is no controlled same-hardware NInfer-versus-llama.cpp speed comparison, no true per-token p95 with MTP4, and no full Terminal-Bench sample under redundancy. SSD mode, parallel requests, long-running stability, and strict completion between consecutive decode calls remain unverified.

The remote source, binaries and logs are isolated under `/tmp/kvmem-ninfer-gc-20261028`; no model weights were copied there.
