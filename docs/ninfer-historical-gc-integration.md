# Historical KV GC on NInfer: integration and acceptance record

This branch gives the pinned NInfer backend opt-in `--kvmem-gc-lru` and `--kvmem-gc-redundancy` modes. Both use the same Host-page lifecycle: the policy proposes victims; the native adapter checks protection, tombstones committed pages, detaches Host records at a safe foreground boundary, and the worker releases them after readers finish. The redundancy mode uses the portable strategy rather than renaming LRU. The modes are mutually exclusive. NInfer results are separate from llama.cpp results.

## Native design

- NInfer uses 64-token Host pages. Only complete, sealed pages enter GC. Sink, recent, active-window, image and in-flight append pages remain protected. Query-selected pages and the Query-replay checkpoint are protected only while prefill still needs them. Optional old checkpoints yield to GC: every catalog/archive alias that requires a retired page is revoked before the next selection. A protected page may be a redundancy witness but cannot be retired. Retired pages are excluded from Query, Pressure and checkpoint selection.
- The foreground copies each sealed page's Mean-K descriptor once into `HistoricalKvPageFeatures`. The GC worker reads an immutable descriptor and a frozen importance snapshot; it never reads mutable NInfer or CUDA state directly. The same page manager accepts an injected LRU or redundancy policy.
- Redundancy mode requires `--kvmem-query-scorer meanq-cosine`. NInfer's normal prefill accumulates accepted Mean-Q for the whole input Query. The foreground publishes updated page scores at most every 1,024 accepted tokens and at Query completion. This also covers long requests for which native working-set retrieval skips Query replay. The GC worker refreshes importance before ranking without repeating Query dot products. Sampled generated-output attention can raise a page's importance; successfully accepted thinking tokens mark the thinking-priority tier.
- Redundancy comparisons use at most 56 pages per round, with age-stratified older candidates and a recent segment. The policy distinguishes proven direct substitutes above cosine 0.9 from capacity fallback victims. An audit log records reason, importance, similarity and retained witness for each proposal. This is a bounded approximation, not an all-history pairwise proof.
- Native Host admission uses physical capacity. Low/high free-page watermarks include headroom for the next prefill burst. The prefill lookahead now skips an allocation when there is insufficient physical room; the next prefill boundary waits up to two seconds for a prepared GC batch and can release detached Host owners immediately. Reader leases retain their charge until readers finish. Decode boundaries continue to defer physical destruction to the worker. The adapter currently allows one active request because independent sequence directories do not coordinate one shared Host budget. Rollback truncates discarded descriptors and thinking ranges; when no proven thinking span remains it disarms thinking-only selection.
- The backend is pinned to `63428ac249da` plus 21 ordered patches. `backends/versions.json` records the SHA-256 of the redundancy, thinking-fallback, prefill-admission and protection-lifecycle patches and the exact prepared source tree.

## Long-decode capacity regression and preliminary latency comparison, 2026-10-30

- A repeatable isolated runner is in `scripts/ninfer_gc_acceptance.py`. It starts a fresh model container for every mode/request, keeps raw streamed responses and native server logs, and treats an SSE `stream_error` as failure even when the HTTP status is 200. Each container resets model and Host KV state. The 9-case short matrix (off/LRU/redundancy x arithmetic/needle/sequence) passed all exact answer checks; both GC modes reclaimed about 79-80 Host pages per case. The first matrix launch had a runner readiness race and is excluded; `acceptance-20261030-rerun1` is the valid matrix.
- A 5,120-token, 16K-context stress request exposed a real redundancy-mode capacity failure. With a 160 MiB Host pool and 5,120-token generation reserve, the old code emitted an SSE `stream_error: native KV RAM capacity exhausted` after roughly 2,900 output tokens, although HTTP remained 200. The same profile in LRU mode completed 5,120 tokens. Once the preferred thinking tier had no selectable sealed page, redundancy stopped proposing victims while unclassified Host pages still occupied capacity.
- NInfer now opts in to the portable policy's cold unclassified-page LRU fallback only when its preferred thinking/reply tier has no selectable victim. Sink, mandatory and active pages remain protected; proposals carry the page's content version and are revalidated at commit. The default portable policy remains unchanged for llama.cpp. The audit marks these as `lru_fallback`, distinct from proven `redundancy` and lossy `capacity_fallback`. A Host regression covers a protected-only thinking tier and a stale prior incarnation. The final native binary rebuilt successfully after the last stale-page filter; its final IQ3 arithmetic request returned HTTP 200, answer `599`, 80 committed/reclaimed pages: 54 redundancy, 25 capacity fallback, 1 LRU fallback.
- The 5,120-token profile has three results per mode; the repaired redundancy mode was repeated three times, with mode order varied. Every request completed 5,120 output tokens with `finish_reason=length`, passed the checked output prefix, and had no SSE error. Redundancy reclaimed 123, 122 and 123 Host pages. Its first run used LRU fallback for all 123 proposals; the next two used 28 redundancy and 94-95 LRU fallback proposals. The stress checker verifies the first 100 numbers in order and at least 1,000 numbers emitted; it does not claim the requested 1-2,000 list was completed. The final stale-incarnation filter was added after these long runs, then covered by the Host test and the final native rebuild plus short IQ3 request.
- The observed p95 of intervals between streamed decode-round timing samples (ms, three runs each) was off: 63.757/66.652/66.756, LRU: 63.980/67.103/64.972, redundancy: 63.355/63.830/66.022. The respective means were 65.722, 65.352 and 64.402 ms. Mean reported decode throughput was 68.155, 68.654 and 69.593 tokens/s. These are preliminary observations, not a demonstrated speedup or a formal <=5% tail-latency result: MTP4 batches multiple tokens in 1,234 of 1,252 observed intervals, so these p95s are per decode round, not per token. GC-off needed a 256 MiB Host pool to finish while GC modes used 160 MiB. Differences in memory allocation and run order also limit causal comparison.
- Evidence is under `/tmp/kvmem-ninfer-gc-20261028/acceptance-decode-5120-repeat2`, `acceptance-decode-5120-repeat3`, `acceptance-decode-gc-5120-fallback-20261030`, `acceptance-decode-gc-5120-lru-20261030`, and `acceptance-final-source-20261030`. The first GC-off record is separately under `/tmp/kvmem-ninfer-gc-20261030/acceptance-decode-5120-off-final`. The original failing redundancy record is retained in `acceptance-decode-gc-5120-20261030`. These are isolated acceptance requests, not Terminal-Bench rewards.
## Equal-Host ordinary-decode pilot, 2026-10-30

- To measure individual decode steps rather than MTP rounds, the runner now accepts `--spec none` and a fixed prompt length via `--records`. A 12,223-token prompt (450 records), 512-token output cap, 128-token thinking cap, 2,048-token active budget, 512-token generation reserve, 16K context and **the same 256 MiB Host pool in all three modes** made GC fire while the off mode also fit. Containers and Host KV were reset between cases; mode order was varied over three repetitions.
- Every off, LRU and redundancy request returned HTTP 200, no SSE error, `finish_reason=length`, and the checked prefix of 100 ordered numbers. LRU and redundancy each committed and reclaimed nine Host pages per request. All nine redundancy-mode proposals in each repetition were `lru_fallback`; this profile measures the cost of the redundancy-mode integration and fallback, not the quality or runtime of a redundancy-scored victim.
- The stream covered `predicted_n=1..512`. It contained 486 single-token intervals and one 25-token interval spanning the thinking-to-answer control transition (128 to 153); thus the single-token p95 excludes that aggregate transition. Single-token p95 values in ms were off 36.958/35.732/37.157 (mean 36.616), LRU 36.502/37.225/36.058 (mean 36.595), and redundancy 36.271/38.009/36.487 (mean 36.922). Mean reported decode throughput was off 29.86, LRU 29.85 and redundancy 29.67 tokens/s. The redundancy mean p95 was 0.84% above off, but one paired run was 6.37% above off. Three runs and the control-token gap do not establish a strict <=5% p95 guarantee.
- Native ordering is visible in code and logs: `prepare_window()` calls `progress_historical_gc()` before active-window selection; `commit_boundary()` sets `retired_pages`, and `memory_page_selectable()` excludes those pages from later candidates. A prepared batch is therefore marked before the next selection. The worker still polls every 25 ms; there is no hard guarantee that every adjacent pair of decode calls contains a newly prepared GC batch. Physical Host-record destruction is asynchronous.
- Raw cases: `acceptance-no-mtp-equal-host-probe450-20261030`, `acceptance-no-mtp-equal-host-controls-20261030`, `acceptance-no-mtp-equal-host-repeat2-20261030`, and `acceptance-no-mtp-equal-host-repeat3-20261030` under the isolated remote root. The 420-record exploratory case had no GC and is excluded from this comparison.

## Agent-prefix capacity replay and official pilot, 2026-10-30

- An actual Terminal-Bench 2.1 `cancel-async-tasks` redundancy pilot at 2,048 active tokens, 1,024 generation reserve, MTP4 and a 96 MiB Host pool made eight successful model calls. The ninth failed with HTTP 500 before the verifier ran; Harbor recorded an exception with **no official reward**, which is not a zero score. The original final prefill had 80 native Host pages in an 82-page pool, while the worker proposed only two preferred thinking victims. This exposed a policy gap: a few preferred victims prevented the cold unclassified fallback from filling the rest of the capacity request.
- The policy now first emits its bounded thinking-tier redundancy or lossy capacity decisions, then fills any remaining demand in the same round from selectable unclassified pages ordered by LRU. Mandatory and currently protected pages are excluded; commit-time protection and content-version checks still apply. A six-page Host regression covers a mixed batch with one thinking victim, two unclassified fallback victims and mandatory pages that must remain live.
- A controlled replay sent the same 17 saved Agent messages in nine requests to a fresh NInfer process. The first repaired 96 MiB run returned HTTP 200 for all nine, but its output lengths differed from the original failure. A second 96 MiB run reproduced the ninth-request failure: 13 pages were proposed and retired at the 8,704-token frontier, but the asynchronous next-chunk prefetch had already raced with their physical release. The native prefill-admission patch now skips unsafe lookahead allocations, waits for the GC worker at the prefill boundary, and drops detached owners promptly there. This work is restricted to prefill; it does not add a wait to token-by-token decode.
- With that final binary, the 96 MiB replay progressed past the former 8,704-token failure point but still returned HTTP 500 later, around 9,648 tokens. At that point all 82 physical Host page slots were occupied and the GC observation reported zero selectable victims; no legal strategy can make a protected page disposable. **96 MiB is therefore not an accepted capacity for this Agent prefix.** The same final binary and same nine input prefixes with a 160 MiB Host pool returned HTTP 200 in all nine requests; the ninth used 8,877 prompt tokens and produced 912 output tokens. Its audit showed 15 redundancy, nine thinking-tier capacity-fallback and 76 unclassified LRU-fallback proposals, of which 70 were committed and physically reclaimed before shutdown. Proposals are not interchangeable with proven duplicate content.
- A separate official `cancel-async-tasks` rerun with the mixed-tier policy and the original 96 MiB pilot settings completed its Agent and verifier without a service or Docker error, but the Agent stopped after three model requests and earned official reward `0.0`. This run preceded the final prefill-admission patch and did **not** trigger GC, so this zero is an Agent/task result, not evidence that the GC strategy caused a quality loss or gain. Its Dockerfile-only pinned-`uv` environment fix and official verifier were unchanged from the prior pilot. The two 96 MiB failures are service-capacity errors without a reward; the completed zero-reward pilot is a distinct outcome.
- Raw evidence is under `harbor-pilot-redundancy-pressure-20261030`, `harbor-pilot-redundancy-pressure-fixed-20261030`, `prefix-replay-series-96-20261030`, `prefix-replay-series-96-fixed-repeat2-20261030`, `prefix-replay-series-96-prefill-admission-20261030`, and `prefix-replay-series-160-prefill-admission-20261030` in the isolated remote root. Every replay started a fresh model process and Host KV state. The 96 and 160 MiB output trajectories are not byte-identical because sampling may diverge, though each request used the same saved input prefix.

## Acceptance boundary

The earlier 96 MiB rejection above is superseded by the protection-lifecycle repair: prefill completion now clears Query-selected IDs, and optional old checkpoint dependencies no longer pin history indefinitely. Their aliases are invalidated if a required page is retired, preserving exact restore validation. The same nine saved Agent input prefixes passed with 96 MiB after this change, with 109 committed/reclaimed pages. Near the final 9,751-token frontier, Host occupancy was 44 pages (all current-view pins), with zero Query/replay pins; the original failure had 82 occupied pages and zero eligible victims. Raw evidence: `protection-lifecycle-96-20261030`. This resolves a conservative-protection defect; it does not establish unlimited execution at every capacity.

Completion qualification uses the 21-patch binary. `scripts/ninfer_gc_latency.py` uses one fresh process per case, identical 320 MiB Host capacity, active 2,048/reserve 512, 16K context, 450 raw-prompt records and 2,048 generated tokens, with victim auditing and transfer tracing disabled. Six permutations balance the ordinary-decode mode order. The declared primary limits are pooled p95 increase <=5% and aggregate decode-throughput decrease <=3%, with per-run worst changes reported. A preflight confirmed complete 2,048-token timing coverage and ten actual redundancy retirements (3,080 comparisons, zero lossy intents). Earlier 1,024-token pilots did not trigger GC and are excluded from that acceptance.

The first long batch exposed thermal drift: cold off-mode throughput was 27.46 tokens/s, the first LRU case was 22.95 (about 16% lower), and the second off case itself dropped to 22.65. GPU telemetry reached 83-84 C. A fixed 512-token warmup still began the first measurement at 73 C and ended at 81 C. Both interrupted batches (`qualification-latency-none-six-20261030`, `qualification-latency-none-steady-six-20261030`) retain completed and partial raw logs plus disposition notes; their adverse measurements are not silently removed. The accepted protocol now warms every case with non-retained, disjoint 512-token requests until the GPU reaches 80 C, at most six attempts, and records temperature/clock/power before warmup, after warmup and after measurement. That rule was fixed before the replacement batch's GC results. Its first hot off case measured p95 48.59 ms and 22.98 tokens/s. The completed steady-state ordinary-decode batch (`qualification-latency-none-steady80-six-20261030`) contains 18/18 HTTP-200 requests, complete 2,048-token timing coverage in every case and no SSE error. Each mode contributes 12,282 single-token intervals. Pooled p95 is off 50.2942 ms, LRU 50.1717 ms and redundancy 50.3529 ms. Aggregate throughput is respectively 22.5455, 22.2775 and 22.4767 tokens/s. Against off, LRU changes p95 by -0.244% and throughput by -1.188%; redundancy changes p95 by +0.117% and throughput by -0.305%. Both pass the declared aggregate limits. Per-run worst changes remain visible: LRU throughput falls 3.368% in repetition 3 (above the 3% single-run reference), and its worst p95 rise is 1.156%; redundancy's worst p95 rise is 2.642% and worst throughput fall 2.864%. Every GC case commits/reclaims ten pages; redundancy executes 3,080 comparisons with zero lossy intents per case. Pooled p99 is off/LRU/redundancy 51.7109/51.4968/51.7251 ms. The maximum individual interval is 56.4705/59.4198/102.2606 ms: redundancy has an isolated 102.26 ms pause at repetition 4, output token 771, confirmed by a 102.17 ms client interval. With tracing disabled its cause is unattributed; the aggregate p95 pass must not be presented as zero interference or a hard per-token deadline guarantee. Native cumulative timing uses wall time from the first accepted token, including intervening foreground work. Independently pooled client arrival p95s are 50.3041/50.1811/50.3452 ms for off/LRU/redundancy, consistent with the native measurement.

The matched MTP4 batch (`qualification-latency-mtp-steady80-three-20261030`) contains 9/9 HTTP-200 requests with 2,048 generated tokens and no SSE error. Pooled **decode-round** p95 is off 84.4205 ms, LRU 84.2200 ms and redundancy 84.4613 ms; aggregate throughput is 48.6815/48.6303/48.8397 tokens/s. LRU's aggregate round p95/throughput changes are -0.237%/-0.105%; redundancy's are +0.048%/+0.325%. Worst paired round-p95 increase/throughput decrease is 0.546%/0.555% for LRU and 0.239%/0.082% for redundancy. All GC cases reclaim nine pages and redundancy performs 3,080 comparisons with zero lossy intents. MTP round p99 is off/LRU/redundancy 85.4725/85.0308/85.4951 ms; maximum observed round intervals are 89.0589/91.6608/87.9236 ms. MTP/native ngram speculation batches tokens, so these p95s do not establish per-token MTP latency or a causal throughput improvement. These two batches exercise a 2K active working set; a separate matched 96K long-context profile is queued to check the larger teacher configuration.

Native LRU and redundancy mode, Host-page retirement under pressure, MTP continuation, full accepted input Query scoring, and a different-prefix reset have been exercised. Both 96 and 160 MiB Agent-prefix replays now have successful single-request integration evidence, with the earlier 96 MiB failures retained above for provenance. This is not a claim of superior task reward or throughput. The small Host pools deliberately force GC and are not the teacher's 256K historical token budget. Native 64-token pages and at least one recent page differ from the earlier llama.cpp 32/0 setting.
